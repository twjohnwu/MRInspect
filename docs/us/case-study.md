# Case study: one multi-lane review on the demo project

One diff, three lanes, one posted review — traced end to end.

[繁體中文版](../tw/case-study.md)

Everything below comes from this repo: the fixture diff, the project files under `projects/`, and the recorded output in [`eval/REPORT.md`](../../eval/REPORT.md) and [`eval/RETRIEVAL.md`](../../eval/RETRIEVAL.md). The demo project is fiction — margherita-pizza, fried-chicken, dough-service and the specs the review read were written for this repo and belong to no one.

## The change

The fixture is [`eval/fixtures/03-lane-overlays-config.diff`](../../eval/fixtures/03-lane-overlays-config.diff), which `eval/fixtures/README.md` lists as kind `config`, picked for being a settings-only change about lane overlay semantics. The diff drops the shared `docs` tag from the `margherita-pizza-docs` and `fried-chicken-docs` sets in `projects/resources.yaml`, so those sets are now tagged with their own system name only. It adds two overlay files, `projects/margherita-pizza/lanes.yaml` and `projects/fried-chicken/lanes.yaml`, each pinning the `spec-conformance` lane to that system's own set with an empty tag list. The remaining hunks update two design notes: a section in `design-be.md` recording the retraction and the reason for it, and a task line in `tasks.md` flipped from `[ ]` to `[x]`. No Go code is touched.

## Lanes resolved

All three lanes declared in `projects/lanes.yaml` are enabled: `spec-conformance`, `standards`, and `code-diff`. `projects/registry.yaml` maps services to systems (`dough-service` and two siblings to `margherita-pizza`, three others to `fried-chicken`) and names `margherita-pizza` as the default system, which is the system this run resolved against.

From there each lane picked up a different resource selector:

- `spec-conformance` took the overlay in `projects/margherita-pizza/lanes.yaml`, which names the set `margherita-pizza-docs` and no tags, replacing the canonical entry's `docs` tag selector.
- `standards` kept its canonical selector, a `standards` tag, which matches the `shared-standards` set in `projects/resources.yaml`.
- `code-diff` names neither a set nor a tag, so it retrieves nothing and sees only the diff.

No lane file sets a TopK, so all three fall back to `DefaultLaneTopK = 8` (`internal/lane/registry.go:35`), and the retrieval report records k = 8 for both retrieving lanes. How overlays, sets, and tags resolve is documented in [Project system](project-system.md); the surrounding review flow is in [Architecture](architecture.md).

## What was retrieved

These are the two rows for this fixture in `eval/RETRIEVAL.md`, generated by the offline retrieval check described in [Configuration](configuration.md#offline-retrieval-check):

| lane | set | k | recall_off | recall_on | mrr_off | mrr_on |
|---|---|---:|---:|---:|---:|---:|
| spec-conformance | margherita-pizza-docs | 8 | 1.00 | 1.00 | 1.00 | 1.00 |
| standards | shared-standards | 8 | 1.00 | 1.00 | 1.00 | 1.00 |

Recall@k is the share of the chunks marked relevant in `eval/retrieval-golden.yaml` that appear in the top k results; MRR is the reciprocal rank of the first relevant chunk, averaged over the queries. The `_off` and `_on` pairs are the same query run against a store with the embedding rerank disabled and enabled (`internal/retrievaleval/run.go:130-179`). The `code-diff` lane retrieves nothing and so has no row.

```markdown
- **standards** — Resource sets: shared-standards (8 chunks retrieved)
- **code-diff** — Resource sets: none

### Findings
| # | Severity | Category | Standard | Item | File:Line |
|---|----------|----------|----------|------|-----------|

```

The rest of the block is short. Three severity sections follow the findings table — High, Medium, Low — and each contains the single line `- None.`; the closing `### Verdict` section reads `Approved`. The same fixture section also records the `single` and `reflect` modes, which produce a differently shaped review from the same diff without lane retrieval; those blocks are longer and list positive observations, and they are in the report next to this one.

## What it cost

`eval/REPORT.md` prints a prompt-composition breakdown per model call and a `Token subtotal: 45351` for this fixture, covering all three modes it ran. The multi-lane mode accounts for three of those calls, one per lane, at 2,516, 2,359, and 1,859 estimated prompt tokens.

The largest lines in the `spec-conformance` lane's 2,516-token prompt:

| Section | Tokens | % of total |
|---|---:|---:|
| diff | 1107 | 44.0% |
| margherita-pizza-docs | 641 | 25.5% |
| base prompt/metadata | 510 | 20.3% |

The other two lanes carry the same 1,107-token diff and the same 510-token base prompt; the `standards` lane adds 495 tokens of retrieved `shared-standards` text and `code-diff` adds none. That retrieved text is most of the 657-token spread between the largest and smallest lane prompt — the remaining 16 tokens are the lane template preamble, 67 for `spec-conformance` against 51 for `code-diff`.

## What this does and does not show

This is one fixture, one model, one run: `gemini-3.6-flash`, recorded 2026-09-05 and 2026-09-06 (the run was split across two days by a free-tier daily quota). The documents it retrieved are fictional specs written for the demo project, so the review's judgment about them says nothing about how the tool behaves on a real codebase. The retrieval numbers measure whether the chunks marked relevant in the golden file came back, not whether the review was any use; nothing here scores review quality, and MRInspect has no external adopters whose results could be cited instead.

The full record for all four fixtures across all three modes is `eval/REPORT.md`, and the retrieval table for all of them is `eval/RETRIEVAL.md`.
